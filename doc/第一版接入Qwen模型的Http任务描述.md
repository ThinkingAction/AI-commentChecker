# Java 接入 Qwen OpenAPI 第一版 MVP 思路

## 1. 第一版目标

第一版的目标是先完成 Java 后端到 Qwen OpenAPI 的最小调用闭环。

核心目标：

> 后端能够读取配置，构造 Qwen 请求，通过 HTTP POST 调用接口，拿到模型返回文本，并返回给业务层。

---

## 2. 第一版需要完成的能力清单

第一版需要完成以下能力：

1. 能读取 API Key。
2. 能配置 endpoint。
3. 能指定模型名称。
4. 能配置 `temperature`。
5. 能配置 `max_tokens`。
6. 能构造 `model + messages + temperature + max_tokens` 请求结构。
7. 能通过 HTTP POST 调用 Qwen。
8. 能拿到模型返回文本。
9. 能处理 HTTP 非 2xx 错误。
10. 能处理响应为空。
11. 能把结果返回给业务层。

---

## 3. 配置项设计

第一版需要以下核心配置项：

| 配置项         | 说明                    |
| ----------- | --------------------- |
| API Key     | 调用 Qwen OpenAPI 的鉴权密钥 |
| endpoint    | Qwen OpenAPI 的请求地址    |
| model       | 当前要调用的 Qwen 模型名称      |
| temperature | 控制模型输出随机性             |
| max_tokens  | 控制模型最大输出长度            |

### 设计说明

API Key 不应该写死在代码中，应该从配置文件、环境变量或配置中心读取。

endpoint、model、temperature、max_tokens 也应该配置化，避免后续调整模型参数时修改代码。

---

## 4. 请求结构设计

第一版请求体关注四个核心字段：

| 字段          | 是否必需 | 第一版是否加入 | 说明             |
| ----------- | ---: | ------: | -------------- |
| model       |    是 |       是 | 指定调用哪个 Qwen 模型 |
| messages    |    是 |       是 | 传递给模型的消息内容     |
| temperature |    否 |       是 | 控制模型输出随机性      |
| max_tokens  |    否 |       是 | 控制模型最大输出长度     |

### 说明

`model` 和 `messages` 是接口调用的核心必传字段。

`temperature` 和 `max_tokens` 虽然不是接口必传字段，但第一版 MVP 中建议直接加入，原因是：

1. `temperature` 可以控制模型输出稳定性。
2. `max_tokens` 可以限制模型输出长度。
3. 这两个参数有利于后续业务结果可控。
4. 配置化后后续调整成本很低。

---

## 5. messages 结构设计

`messages` 是一个消息数组，用于告诉模型当前任务是什么、用户输入是什么。

第一版建议只使用两类消息：

| role   | 作用               |
| ------ | ---------------- |
| system | 定义模型角色、任务规则、输出要求 |
| user   | 传入本次用户输入内容       |

### 构造思路

第一版调用时，可以按下面的逻辑构造：

| 消息顺序  | role   | 内容来源       |
| ----- | ------ | ---------- |
| 第 1 条 | system | 后端预设的系统提示词 |
| 第 2 条 | user   | 业务层传入的用户内容 |

---

## 6. temperature 参数说明

`temperature` 用来控制模型输出的随机性。

| 值范围 | 效果                  |
| --- | ------------------- |
| 较低  | 输出更稳定、更保守、更适合分类和审核  |
| 较高  | 输出更发散、更有创造性，适合开放式生成 |

### 第一版建议

如果当前主要用于评论审核、分类、信息抽取，建议第一版设置为：

```text
0.1 ~ 0.3
```

推荐默认值：

```text
0.2
```

原因：

1. 评论审核不需要太强创造性。
2. 分类任务更需要稳定输出。
3. 较低 temperature 可以减少同一输入多次调用结果不一致的问题。

---

## 7. max_tokens 参数说明

`max_tokens` 用来限制模型最多生成多少 token。

### 第一版建议

如果当前返回内容较短，例如评论审核结果、分类结果、简单问答，建议设置为：

```text
512 ~ 1024
```

推荐默认值：

```text
1024
```

原因：

1. 防止模型返回过长内容。
2. 控制调用成本。
3. 控制接口响应时间。
4. 避免业务层接收到超出预期的大段文本。

---

## 8. 请求发送流程

Java 后端通过 HttpClient 调用 Qwen 的流程如下：

1. 从配置中读取 API Key。
2. 从配置中读取 endpoint。
3. 从配置中读取 model。
4. 从配置中读取 temperature。
5. 从配置中读取 max_tokens。
6. 接收业务层传入的用户内容。
7. 构造 system message。
8. 构造 user message。
9. 将 model、messages、temperature、max_tokens 组装成请求体。
10. 将请求体转换为 JSON。
11. 创建 HTTP POST 请求。
12. 设置 Authorization 请求头。
13. 设置 Content-Type 请求头。
14. 发送请求到 Qwen endpoint。
15. 接收 Qwen 返回结果。

---

## 9. 响应解析流程

Qwen 返回结果后，第一版只需要关注模型最终返回文本。

处理流程如下：

1. 获取 HTTP 响应状态码。
2. 判断状态码是否为 2xx。
3. 如果不是 2xx，认为调用失败。
4. 如果是 2xx，继续解析响应体。
5. 判断响应体是否为空。
6. 如果响应体为空，认为调用失败。
7. 从响应体中提取模型回复文本。
8. 将模型回复文本返回给业务层。

---

## 10. HTTP 非 2xx 错误处理

第一版必须处理 HTTP 非 2xx 的情况。

例如：

| 状态码 | 可能原因          |
| --- | ------------- |
| 400 | 请求参数错误        |
| 401 | API Key 错误或未传 |
| 403 | 无权限访问该模型或接口   |
| 404 | endpoint 配置错误 |
| 429 | 请求过多，被限流      |
| 500 | Qwen 服务端异常    |

### 处理原则

第一版不需要做复杂重试，只需要：

1. 判断状态码不是 2xx。
2. 记录状态码。
3. 记录响应内容。
4. 抛出统一调用异常。
5. 不继续解析模型结果。

---

## 11. 响应为空处理

即使 HTTP 状态码是 2xx，也可能出现响应体为空、响应结构异常、模型内容为空等情况。

第一版需要处理以下情况：

| 异常情况         | 处理方式   |
| ------------ | ------ |
| 响应体为空        | 返回调用异常 |
| 响应 JSON 无法解析 | 返回调用异常 |
| choices 为空   | 返回调用异常 |
| message 为空   | 返回调用异常 |
| content 为空   | 返回调用异常 |

### 处理原则

只要无法拿到有效的模型文本结果，就不要返回空字符串给业务层，而是明确返回调用失败。

---

## 12. 返回给业务层的内容

第一版 Qwen Client 对业务层只返回一个核心结果：

> 模型生成的文本内容

也就是说，业务层不需要关心：

* HTTP 请求怎么发
* API Key 怎么拼
* Qwen 响应结构是什么
* choices 在哪里
* content 在哪里
* HTTP 错误怎么判断

这些都应该封装在 Qwen Client 内部。

---

## 13. 第一版推荐分层

第一版可以采用简单分层：

```text
业务 Service
  ↓
Qwen Client
  ↓
Qwen OpenAPI
```

### 业务 Service 职责

业务 Service 负责：

1. 接收业务输入。
2. 组织业务问题。
3. 调用 Qwen Client。
4. 接收模型返回文本。
5. 将结果返回给上层业务。

### Qwen Client 职责

Qwen Client 负责：

1. 读取 Qwen 配置。
2. 构造 Qwen 请求。
3. 发送 HTTP POST 请求。
4. 判断 HTTP 状态码。
5. 解析 Qwen 响应。
6. 提取模型返回文本。
7. 处理调用异常。

---

## 14. 第一版完整调用链路

第一版完整链路如下：

```text
业务层传入文本
  ↓
读取 API Key
  ↓
读取 endpoint
  ↓
读取 model
  ↓
读取 temperature
  ↓
读取 max_tokens
  ↓
构造 messages
  ↓
组装 Qwen 请求体
  ↓
发送 HTTP POST 请求
  ↓
判断 HTTP 状态码
  ↓
解析响应体
  ↓
提取模型返回文本
  ↓
返回给业务层
```

---

## 15. 第一版验收标准

第一版完成后，应该满足以下验收标准：

| 验收项                                             | 是否必须 |
| ----------------------------------------------- | ---: |
| 能正确读取 API Key                                   |    是 |
| 能正确读取 endpoint                                  |    是 |
| 能正确读取 model                                     |    是 |
| 能正确读取 temperature                               |    是 |
| 能正确读取 max_tokens                                |    是 |
| 能构造 model + messages + temperature + max_tokens |    是 |
| 能成功发送 HTTP POST 请求                              |    是 |
| 能拿到 Qwen 返回文本                                   |    是 |
| HTTP 非 2xx 时能识别失败                               |    是 |
| 响应为空时能识别失败                                      |    是 |
| 能把正常结果返回给业务层                                    |    是 |

---

## 16. 第一版边界

第一版只做最小可行能力，不做额外扩展。

本阶段不处理：

* 流式输出
* 多轮对话
* 多模型切换
* Prompt 模板管理
* JSON 格式校验
* 自动重试
* 兜底人工审核
* token 统计
* RAG
* Agent
* 工具调用

---

## 17. 总结

Java 接入 Qwen OpenAPI 的第一版，只需要完成一个最小闭环：

> 读取配置 → 构造 model + messages + temperature + max_tokens → HTTP POST 调用 Qwen → 解析模型文本 → 返回给业务层。

第一版重点不是功能复杂，而是调用链路清晰、职责边界明确、异常情况可控。
